# AVCoders.Dsp

Audio DSP drivers for the [AV Coders device library](https://github.com/AV-Coders/c-sharp-device-library). Built on `AVCoders.Core`. Targets **.NET 8.0 and .NET 10.0**.

## Install

```bash
dotnet add package AVCoders.Dsp
```

Published to [nuget.org](https://www.nuget.org/packages/AVCoders.Dsp). See the [repository README](https://github.com/AV-Coders/c-sharp-device-library) for details.

## Drivers

- `BiampTtp` — Biamp Tesira
  - Shows the Tesira's model, revision, firmware, serial number, hostname, network interfaces and DNS as details. They're read on connect and on each `Reinitialise`, which also runs every few minutes while idle
  - Instance tags the driver uses that aren't in the Tesira's configuration show as Missing Controls, with an issue for each
  - The idle keep-alive reads the active fault list every 10 s and raises each fault as an issue. Its round trip shows as Reply Time. A reply slower than `BiampTtp.SlowKeepAliveReplyMs` (500 ms) raises an issue, and one missing after `BiampTtp.KeepAliveReplyWindowMs` (1 s) is flagged straight away. `BiampTtp.MaxSlowKeepAlives` slow or `BiampTtp.MaxMissedKeepAlives` missed keep-alives in a row reconnect the session, which clears the TTP slowdown in older firmware
  - Raises an issue when the firmware is below 4.11, which isn't supported, or is a 5.x below 5.7
  - A read the Tesira answers with `-ERR ATTRIBUTE_NOT_SUPPORTED` or `-ERR '<attribute>' is not supported by ...` shows `Not supported: ` and the raw reply in its details (the fault list in Active Faults), with no issue. Any other `-ERR` to a read counts as a miss and keeps the last value: the third in a row raises a Minor issue carrying the raw reply, and the next good reply resolves it
  - A reply to one of those reads (or the fault list) that can't be read shows the raw line in its details in warning tone and is read again at the next `Reinitialise` (the fault list at the next keep-alive). The third in a row raises a Minor issue carrying the raw line, and the next good reply resolves it. An empty firmware or serial number string shows the raw line with no issue
  - Every subscription is sent again on connect and on each `Reinitialise`, since the Tesira drops them when it reboots (Biamp, *Tesira Text Protocol*, `Tesira Text Protocol.pdf` p. 4: "they can be recreated by subscribing to the same block at regular intervals") or loads a new configuration. A re-subscribe the Tesira answers with `-ERR ALREADY_SUBSCRIBED` means the subscription is still in place: it counts as answered and is logged at Verbose, with no issue. That reply isn't in the manual; it's what firmware 5.2.0.8 answers. Any other `-ERR` to a set, preset recall or subscription raises the momentary `error-reply` issue, which names the reply and the command: `The Tesira returned <reply> to <command>`
  - The `+OK` or `-ERR` that answers a set, preset recall or subscription is logged under the trigger id of the call that sent it, so `/Logs?trigger=` shows the command and its reply together
- `QsysEcp` — QSC Q-SYS
  - A control the Core doesn't know (`bad_id "<name>"`) shows in Missing Controls, with an ongoing `bad-control:<name>` issue until it reports a value
  - A blank control name (empty or whitespace) for a level, mute, string or meter is never added to a change group or read (`cga`/`cg`). It's logged with the raw name and shows as `""` in Missing Controls. Each blank control raises its own ongoing issue, keyed by the raw name, its type and its registration order (e.g. `bad-control:"" level 1`), so none is hidden. A Core answers an empty name with `bad_id ""`, which raises `bad-control:`
  - `SetLevel`, `SetAudioMute` and `SetValue` send nothing for a blank control name, and log a Warning with the raw name
  - Pass an optional `RestComms` for Core Manager (`https`, `QsysEcp.CoreManagerPort` 443), plus a username and password when Access Control is on, to show the Core's firmware, serial number and hardware ID as details. They're read on connect and on each design redeploy. With a username the driver logs on first and reads with the token, keeps the token across reconnects, and logs on again only when Core Manager refuses it
  - A Core Manager HTTP 404, which is what firmware without that API returns, shows `Not supported: ` and the raw reply in those details, with no issue. Any other failure raises the Minor `core-manager` issue
  - `RecallSnapshot(name, n)` sends `ssl "<name>" <n> 0`, loading snapshot `n` of the bank `name` with no ramp. `RecallSnapshot(name, n, rampTime)` loads it over `rampTime` seconds
  - `QsysVolumeControl` — a level and a mute as one `VolumeControl`
  - `QsysVolumeOnlyControl` — a level with no mute (`SupportsMute` is `false`)
  - `QsysMuteOnlyControl` — a mute with no level (`SupportsLevel` is `false`)
  - The three controls take any `Dsp`, so they drive `QsysQrc` too
- `QsysQrc` — QSC Q-SYS over QRC (JSON-RPC on TCP 1710, UTF-8, each message ending in a NUL), for designs that expose named components rather than named controls. Untested against a Core: its tests use invented replies. Two QRC programs that work on the CHES Cores (the legacy 3-03 room's QSYSControlV4_2 and the keypad rooms' QscQsys) agree with it on the logon reply (`result: true`), levels as `Position` (proven for named controls), mutes as `Value` 1/0, and change-group polls arriving as `ChangeGroup.Poll` notifications whose `params.Changes` carry `Name`, `Value`, `String` and `Position`
  - `QsysEcp` and `QsysQrc` share `QsysDsp`: the level, mute and string registries, Missing Controls, the `bad-control:<name>` issues (a blank name gets its own, keyed by its type and registration order, e.g. `bad-control:"" level 1`), the reconnect after three unanswered status requests, and `RecallSnapshot(name, n)`, so a room can drive either driver as a `QsysDsp`. Each driver sends its own command for it
  - A control name is `<component>.<control>`, e.g. `Room.gain`. A name with no component raises an ongoing `bad-control:<name>` issue and is never sent
  - With one dot, the component is the text before it. With more (`Main Mixer.input.1.gain`, `Lobby.Zone 1.gain`) the driver asks the logged-on Core for its components (`Component.GetComponents`) and takes the longest listed component the name starts with. Names with one dot never wait for that list, and it's only asked for when a control or set has a name with more. A name with more than one dot that no listed component starts, or any such name when the Core rejects or doesn't answer the list, raises its `bad-control:<name>` issue with the reason and is not sent. The list is kept across reconnects and asked for afresh after a design redeploy; after a rejection or no answer it's asked for again on the next connection or `Reinitialise`
  - Logs on with the username and password when the Core sends `EngineStatus` (or answers `StatusGet`), and skips the logon when both are blank. The logon counts only on `result: true`; any other answer raises a Critical `login` issue carrying the raw reply. Error 10 (logon required) to a later command logs on again and sends that set after it, unless a newer set for the same control is waiting. One logon is in flight at a time, and at most two (as QSC's QscQsys allows) until the Core answers a command other than the logon; past that the Critical `login` issue carries the raw reply and the driver stops logging on
  - A refused logon stays one ongoing `login` issue, and the communication state stays out of Okay (so the `communication` issue stays one entry too), across reconnects until a logon succeeds. A logon the driver stopped is tried again after each poll, on `Reinitialise`, and on each new connection
  - A logon the Core hasn't answered by the first poll after the reply timeout raises the Critical `login` issue showing the logon as sent, with the password masked, and the driver reconnects
  - The password never reaches a log or the comms console. The driver has the client mask `"Password":"<password>"` (`MaskInRequests`), so the client's Verbose `Sending` lines and its string and byte request handlers show `"Password":"***"`, while the Core gets the real one
  - While the client isn't connected, a set goes straight to the client: it queues it for its queue timeout, reconnects for it when a person made it while the client was disconnected on request, and drops it when no person did. The exception is a set on a name with more than one dot before the driver has ever had the component list: it can't be split yet, so it waits in the driver and doesn't reconnect the client. Polls send nothing while the client isn't connected
  - While connected but not yet logged on, or for a name with more than one dot until the component list arrives, a set waits in the driver, keeping only the latest per control, and goes in the order it was made. A set the Core answers with error 10 waits for the logon the same way. A waiting set older than the client's `QueueTimeoutFor` limit for it (the queue timeout, 5 s by default, or 15 s for a person's set made while the client was disconnected on request or reconnecting for a send) is dropped with a Warning
  - Replies are matched to requests by id, so a reply's logs and issues carry the trigger id of the command that was sent. A request is tracked with `SentCommandTracker` from when the client writes it (its `RequestHandlers`), so a send that waited in the client's queue isn't timed from when it was made, and a send the client drops is never reported. A written request the Core hasn't answered within `ReplyTimeout` (5 s) is unanswered, checked at each poll; one other than the logon, the component list or a status request is logged as a Warning. Ids never repeat, so requests stay matched across a reconnect: a set written just before a drop and rejected with error 10 after it is still sent again after the logon
  - `Component.Set` "Returns a list of unknown controls after processing" (QSC's QRC manual, which shows no example). A reply listing the set's control, as `["load_7"]` or `[{"Name":"load_7"}]`, or error 7 (unknown component) or 8 (unknown control), raises its ongoing `bad-control:<name>` issue and lists it in Missing Controls; a later set the Core accepts resolves it. Any other rejection raises the momentary `rejected-request` issue
  - After the logon, on every Active `EngineStatus`, and when `StatusGet` reports a new design code, it adds each component's controls to one change group with `ChangeGroup.AddComponentControl` and starts `ChangeGroup.AutoPoll`. A component the Core rejects shows its controls in Missing Controls, each with an ongoing `bad-control:<name>` issue until it reports a value. `Reinitialise` rebuilds the change group and sends `ChangeGroup.Invalidate`, so the Core resends every value
  - Levels are set as positions, mutes as values 1 and 0. `RecallSnapshot(name, n)` sets `load_<n>` on the snapshot component `name`
  - Polls `StatusGet`, showing the design name and code and whether the Core is active; a Core that isn't active raises a Critical `core-standby` issue. Three unanswered polls reconnect. If bytes arrived with no NUL message end (the wrong port, say), the unanswered-status issue shows the first 200 of them, escaped
  - A reply that isn't JSON, isn't a JSON object, or has a duplicate key anywhere in it raises the momentary `unreadable-reply` issue with the raw text; a change-group poll with no list of changes is logged as a Warning with the raw text. A level, mute or string handler that throws is logged as an Error with the raw text, and raises no issue. Either way the rest of the read is handled. Over 8 MB with no NUL message end is dropped with the momentary `unreadable-reply` issue
- `BoseCspSoIP` — Bose ControlSpace. A command the CSP rejects with a NAK raises an issue on its module (e.g. `nak:Bar Gain`), Major for code 01 (no such module, or a duplicate name) and 02 (illegal index), Minor otherwise; it resolves when that module next answers
  - Polls each control with a 30 ms gap between queries
- `YamahaXmv` — Yamaha XMV series power amplifiers (XMV4280, XMV4140, XMV8280, XMV8140 and their -D Dante models) over Yamaha's MTX/MRX/XMV remote control protocol: TCP 49280 (`YamahaXmv.DefaultPort`), one command per line ending in LF. It takes a `TcpClient` made with `CommandStringFormat.Ascii`, since it reads the replies as text. Untested against an amp: its tests use invented replies built from the formats and examples in Yamaha's *Remote Control Protocol Specifications* V3.1.0 (`mtx_mrx_xmv_ex_remote_control_protocol_spec_v310_en.pdf`), plus the LIMIT Indicator meter from V4.0.0
  - A level or mute control name is a channel letter, `A` to `H`. The string controls are `<channel> Polarity` (Normal, Inverse), `<channel> Input Select` (Analog, Digital) and `Input Select` for every channel (Analog, Digital, Multiple). Any other name raises an ongoing `bad-control:<name>` issue, shows in Missing Controls and is never sent. A channel the amp rejects (E to H on a 4-channel model, say) raises the same issue with the amp's raw `ERROR` reply until it reports a value
  - A level is the channel's ATT, -99 to 0 dB, sent and read in hundredths of a dB. That's the spec's general raw-value rule: its XMV table gives no scale for ATT, so check it on an amp. Percent maps to dB through `Fader`, with the curve passed to the constructor (Linear by default, as in `BiampTtp`)
  - `PowerOn` and `PowerOff` set the Power parameter to 0 (on) and 1 (standby), as the spec's Remarks column has it. Its MIN and MAX columns read the other way round, so check this on an amp
  - `QsysVolumeControl`, `QsysVolumeOnlyControl` and `QsysMuteOnlyControl` take any `Dsp`, so they drive an XMV channel too, e.g. `new QsysVolumeControl(new QscAudioBlockInfo("Zone 1", "A", "A"), VolumeType.Speaker, xmv)`
  - On connect it asks `devstatus runmode`, as the spec requires. Once the amp answers `normal`, it reads the alert status, identity, clock and power, gets each registered control and starts the limiter meter. Changes made on the amp or by another controller arrive as `NOTIFY set`. A run mode other than `normal` raises a Critical `run-mode` issue with the raw reply, and the driver sends only the run-mode query until the amp is back to `normal`
  - Polls every 5 s (`YamahaXmv.PollIntervalMs`): the run mode, and once running the alert status and the limiter meter. Three unanswered run-mode queries set communication to Error and reconnect. An unanswered alert-status poll raises the momentary `unanswered-alert-status` issue, which the third in a row makes an ongoing Major one, and the next reply resolves it
  - Each alert the amp reports (`NOTIFY devstatus error`, and the polled `devstatus error`) raises an ongoing `alert:<number>:<message>` issue carrying the raw alert text: Critical for a fault (`flt`), Major for an error (`err`), Minor for a warning (`wrn`). The key carries the alert's message because Yamaha puts the channel there (`[ch*]` in alerts 102, 104 and 105, `channel *` in 110 and 226), so each channel's alert is its own issue. The amp's `off` for that alert resolves it. An alert status of `none` resolves every alert issue, which is how a single-shot alert, which the amp never turns off, is resolved. An alert of any other type raises a momentary Minor issue under its key, once per occurrence. An alert the driver can't read raises an ongoing Major `alert-unreadable` issue with the raw text until the amp reports `none`. The latest alert status shows raw as Alert
  - Alerts x103 (protection shut the power supply down) and x104 (protection muted an output) raise Critical issues, above Yamaha's error type, since both take audio away
  - On each connection, and on `Reinitialise`, the driver reads the amp's alert event log: `event MTX:EventLogGetLogNumber`, then `EventLogGetLogList` ten entries at a time, with the last range overlapping the one before so it stays ascending, or `EventLogGetLog` for a single entry. Each alert's latest entry decides it:
    - An `off` resolves that alert's issue, so an alert that cleared while the connection was down is resolved even while another alert is still on
    - An `on` raises its issue when it's newer than the newest alert the driver had seen: before this connection, for the first read on a connection, or at all, for a `Reinitialise` on the same connection, since every notification on it was seen. The alert status must not be `none`, and that status is forgotten at each connection change
    - The first read after the program starts raises nothing, since there's nothing to compare with, and sets the newest alert seen from the log
    - The latest entry goes by the log's order when its timestamps show one: oldest first or newest first, by most of the steps between neighbouring entries. With no order to go by, it goes by timestamp, and an `on` and an `off` in the same second leave the alert raised. Alert Log shows the entry count and the order found, or `Not supported: ` and the raw reply when the amp rejects the read, with no issue
    - Two limits the protocol leaves. After the program starts, only the alert `devstatus error` reports is raised: other alerts already on stay unknown until they change, since the status is one alert and the log has no baseline yet. And alerts 10 and 13 reset the amp's clock, so log entries made after a reset can look older than earlier ones: one newer than the newest alert seen can then fail to raise, and with no order in the log it can be taken for an older entry
  - The LIMIT Indicator meter (UniqueId 80001, firmware V4.00 and later) is asked for every poll, since the amp stops a meter 10 s after the request, and reports every second. A channel's limiter engaging raises a momentary Minor `limiter:<channel>` issue, counted once per engagement. Limiter shows `Off` or the engaged channels. An amp that rejects the meter shows `Not supported: ` and the raw reply, and isn't asked again until `Reinitialise` or the next connection
  - Shows Model, Firmware, Serial, Device Name, Unit ID, Protocol Version and Parameter Set Version (`devinfo`), Sampling Rate and Word Clock (`devstatus fs` and `lockstatus`, also notified), Run Mode, Alert and Limiter as details. A sampling rate of `unknown` or a word clock of `unlock` shows in warning tone with no issue, since the amp raises its own word-clock alert
  - The identity and clock are read once per connection and on `Reinitialise`. A read the amp rejects with `UnknownCommand`, `WrongFormat`, `InvalidArgument`, `UnknownAddress`, `UnknownEventID`, `TooLongCommand`, `ReadOnly`, `NoPermission` or `InternalError` (whose example in the spec is a parameter that doesn't exist in the device) shows `Not supported: ` and the raw reply, with no issue, and isn't asked again. `Busy`, `AccessDenied`, any other code, a reply with no value, or no reply within `YamahaXmv.ReplyTimeout` (5 s) counts as a miss, and the read is asked again at the next poll. The third in a row raises a Minor `<read>-read` issue (e.g. `firmware-read`) carrying the last raw reply, and the next good reply resolves it. An empty value shows the raw reply and counts as answered
  - A control read the amp answers with `Busy`, `AccessDenied` or another code that isn't a rejection, or doesn't answer, is asked again at the next poll. A rejection (`InternalError` included) shows the channel as a bad control
  - The amp's reply to a set, and its `NOTIFY set`, carry its own display string. A level whose display string disagrees with the driver's hundredths of a dB raises the Major `level-scale:<channel>` issue, with the raw value and the display, until that channel's display agrees. `-INFINITY` agrees with raw -13801, as the spec's section 3.1 has it. Level Display shows the last display string and its raw value, in warning tone when they disagree or the display isn't a number, which isn't checked. Power shows its display string and raw value. A display of `Standby` for a value the driver reads as On, or `ON` for one it reads as Off, raises the Major `power-value` issue. Both are there so a wrong reading of the spec shows on the bench
  - Replies are matched to commands with `SentCommandTracker`, from when the client writes each one: an `OK` or `OKm` by its command and address, and an `ERROR <command> <code>` by its command name. A reply's logs and issues carry the trigger id of the command that was sent. A rejected set raises the momentary `rejected-command` issue naming the command and the reply. Any other `ERROR` raises the momentary `error-reply` issue, which escalates after three in a row
  - Every send goes straight to the client's `Send`: while it isn't connected, the client queues it, reconnects for a person's send made while it was disconnected on request, and drops the rest. Polls send nothing while the client isn't connected
  - A line it can't read raises the momentary `unreadable-reply` issue with the raw line, and the rest of the reply is still handled. A level, mute or string handler that throws is logged as an Error with the raw line. More than 64 KB with no line end is dropped with the same issue
  - The protocol has no login, so there's nothing for `MaskInRequests` to hide
  - Test fixtures: every reply in `YamahaXmvTest` is invented, since no XMV traffic has been captured. Each follows a format or example in the V3.1.0 spec, with the XMV addresses from its section 7.3. The spec has no example of an alert turning off, a fault or warning alert, the XMV's own alert texts, an alert event log's order, or a LIMIT Indicator meter line, so those follow its stated formats. The alert numbers come from Yamaha's XMV alert list (ProVisionaire Amp Editor manual, section 15.3) with invented messages, the event log runs oldest first, and the meter line takes the `raw` type V4.0.0 section 8.3 lists, with two-digit hex values as in the level-meter example in 3.2.3. The spec says commands end with LF and is silent on how replies end: the fixtures end with LF, and CR LF is tested too
- `CecAudioSystem` — a CEC soundbar or AVR (verified on a Sonos Beam). A single `VolumeControl`, not a `Dsp` subclass
  - Frames go out in order, 150 ms apart (100 ms after a key press, 500 ms after a status query, 750 ms after a discovery request). The spacing, the 300 ms status read after a key and the 1.5 s wait for Report Audio Status are awaited, so no thread is held while waiting, and the reply wait's timer is cancelled as soon as the status arrives

## Usage

Drivers derive from `Dsp` (except `CecAudioSystem`, which is a `VolumeControl` over a CEC `SerialClient`) and talk to hardware through a transport from `AVCoders.CommunicationClients`. `Dsp` holds what every DSP driver shares: the communication state while the client isn't connected (Unknown, or NotAttempted while it's disconnected on request), the `bad-control:` issue prefix and the Missing Controls label. `QsysDsp` and `YamahaXmv` also share the level, mute and string registry behind `AddControl`, `GetLevel`, `LevelUp`, `ToggleAudioMute` and the rest, with the `bad-control:<name>` issues and Missing Controls detail it raises, and the reconnect after three unanswered status queries. See the [repository README](https://github.com/AV-Coders/c-sharp-device-library) for full wiring, logging and tracing setup.
